**TL;DR**

- 매일 아침 도는 자동화를 만들었는데 Google 인증이 7일마다 끊겨서 매주 손으로 다시 로그인하고 있었습니다. 자동화하려다 수동 작업이 늘어난 셈입니다.
- 원인은 스크립트 쪽이 아니었습니다. Google Cloud 콘솔의 OAuth 동의 화면이 "테스트" 상태였습니다. 이 상태에서 발급된 토큰은 7일 뒤에 만료된다고 공식 문서에 적혀 있습니다.
- 붙이는 순서를 바꾸면 인증은 한 번으로 끝납니다. 동의 화면 게시 → API 활성화 → 스코프 확정 → 인증 → 서비스별 실호출 순입니다.

매일 아침 캘린더와 메일을 긁어 그날의 노트를 만드는 스크립트를 돌리고 있습니다. 이 스크립트가 일주일에 한 번씩 멈춰 섰습니다. 인증이 풀려서 제가 터미널을 열고 다시 로그인해야 했습니다. 자동화를 하려고 만든 것에 매주 손이 가는 상황이라 뭔가 잘못됐다는 생각이 들었습니다.

원인을 찾는 데 두 달이 걸렸습니다. 알고 보니 코드 문제가 아니었습니다. 같은 자동화를 만들려는 분들이 저와 같은 길을 두 달 돌지 않았으면 해서 정리했습니다.

---

## 1. 서버에서 도는 자동화는 커넥터를 쓸 수 없습니다

Claude나 ChatGPT 대화창에서 Gmail을 연결해 쓰는 건 쉽습니다. MCP 커넥터를 한 번 붙여두면 "지난주 메일 정리해줘" 같은 요청이 바로 됩니다. 그런데 그 방식을 자동화로 옮기려니 처음부터 막혔습니다.

1. **MCP 커넥터는 대화 세션 안에서만 살아 있습니다.** 커넥터의 인증은 지금 열려 있는 대화창에 붙어 있습니다. 대화가 끝나면 그 연결도 같이 사라집니다. 반면 자동화는 사람이 없는 시간에 혼자 돕니다. 제 경우는 맥의 스케줄러(launchd)가 매일 아침 스크립트를 깨우는데 이때는 대화창이 없으니 커넥터도 없습니다. Claude Code를 클라우드에서 돌리는 경우도 마찬가지입니다. 서버에서 실행되는 세션은 제 브라우저에 로그인된 Google 계정을 알지 못합니다. 커넥터가 못 하는 일이 아닙니다. 붙을 자리가 애초에 없습니다.

2. **그래서 CLI로 직접 붙이고 인증도 직접 관리하게 됩니다.** 저는 Google Workspace CLI(gws)를 썼습니다. 터미널에서 Gmail·Calendar·Tasks를 부를 수 있는 도구입니다. 커넥터를 쓸 때는 남이 대신 해주던 일을 이제 제가 해야 합니다. Google에 "나는 이런 프로그램이고 이 데이터가 필요합니다"라고 등록하고 허락을 받아 그 허락증(토큰)을 보관하는 일입니다. 이 글의 나머지는 그 허락증이 자꾸 만료되면서 벌어진 일입니다.

## 2. Google API를 쓰려면 왜 "앱"을 만들어야 할까요

여기서 한 번 짚고 갑니다. 왜 Google Cloud에 프로젝트를 만들고 OAuth 클라이언트를 등록해야 하는지 저도 처음에는 이해가 안 갔습니다.

1. **Google 입장에서는 "누가 요청하는가"가 필요하기 때문입니다.** Google API에 오는 요청은 전부 "어떤 프로그램이 어떤 사용자를 대신해서" 보내는 것입니다. 여기서 프로그램에 해당하는 것이 OAuth 클라이언트, 흔히 말하는 앱입니다. 제가 만든 스크립트도 Google이 보기에는 하나의 앱이고 신분증이 있어야 말을 걸 수 있습니다. 그 신분증이 클라이언트 ID와 시크릿입니다.

2. **동의 화면은 그 앱에게 권한을 주는 자리입니다.** 처음 인증할 때 뜨는 "이 앱이 Gmail에 접근하려고 합니다" 화면이 그것입니다. 사용자가 여기서 허용을 누르면 Google이 앱에게 토큰을 내줍니다. 내 계정으로 내 앱에 허락하는 구조라 자기 자신에게 허락하는 것처럼 보이지만 Google에게는 사용자와 앱이 별개의 주체입니다. 뒤에 나올 문제가 이 구분에서 나옵니다.

## 3. 조용히 죽는 자동화를 두 번 겪었습니다

에러를 내고 멈춰주는 고장은 차라리 낫습니다. 문제는 아무 소리 없이 잘못된 결과가 나오는 쪽입니다.

1. **401을 "결과 0건"으로 읽고 있었습니다.** 401은 인증 실패를 뜻하는 HTTP 상태 코드입니다. 서버가 "당신이 누구인지 확인할 수 없다"고 답한 것이고 대개 토큰이 만료됐거나 잘못됐을 때 나옵니다. 그런데 제 스크립트는 gws가 뱉는 에러 출력을 버리고 있었습니다. 그래서 인증 실패가 그냥 빈 결과로 둔갑했습니다. 노트는 멀쩡히 생기는데 일정 칸만 비어 있었고 이틀 치가 쌓인 뒤에야 알아챘습니다. 지금은 스크립트 맨 앞에 인증 확인용 호출을 하나 심어두고 실패하면 거기서 멈추고 알림이 뜨게 해뒀습니다.

2. **그걸 고쳐놓고 보니 이번엔 7일마다 죽었습니다.** 인증이 풀렸다는 건 이제 바로 알 수 있었는데 다시 로그인하면 멀쩡히 돌아오니 "가끔 풀리는구나" 하고 넘어갔습니다. 그렇게 두 달 가까이 재인증만 반복했습니다. 증상만 잡고 원인은 손도 못 댄 상태였습니다. 그걸 나중에야 인정했습니다.

## 4. 원인은 동의 화면의 게시 상태였습니다

로그에는 이것만 찍혀 있었습니다.

```
$ gws gmail users labels list --params '{"userId":"me"}'
error: invalid_grant
  Token has been expired or revoked.
```

토큰이 만료됐거나 폐기됐다는 말인데 왜 그랬는지는 알려주지 않습니다. 갱신 로직만 몇 번 들여다보고 아무것도 못 찾았습니다.

1. **파일 수정 시각이 주기를 알려줬습니다.** 코드를 그만 보고 자격증명 파일이 언제 바뀌었는지 확인했습니다.

```
$ ls -lT ~/.config/gws/
-rw-------  credentials     Jun 28 00:17
-rw-------  token_cache    Jul  4 11:31
```

인증한 날이 6월 28일, 토큰이 마지막으로 갱신된 날이 7월 4일이었습니다. 6일입니다. 버그라면 이렇게 규칙적으로 죽지 않습니다. 이 숫자를 보고 의심을 코드에서 정책으로 옮겼습니다.

2. **공식 문서가 정확한 기한을 알려줬습니다.** 추측을 확인하려고 Google의 OAuth 문서를 찾아봤더니 이 문장이 있었습니다.

> A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of "Testing" is issued a refresh token expiring in 7 days.
>
> 출처: [Using OAuth 2.0 to Access Google APIs (Refresh token expiration)](https://developers.google.com/identity/protocols/oauth2)

동의 화면이 "테스트(Testing)" 상태면 거기서 발급된 갱신 토큰은 7일 뒤에 만료된다는 뜻입니다. 제가 관측한 6일과 맞아떨어졌습니다. 테스트용으로 만든 앱이 사용자 계정의 권한을 영원히 붙들고 있지 못하게 막는 장치입니다. 개인 프로젝트로 만들어두고 그냥 쓰고 있었으니 계속 테스트 상태였습니다.

3. **해결은 "앱 게시" 버튼 하나였고 사전 심사도 없었습니다.** Google Cloud 콘솔의 대상(Audience) 화면에서 게시 상태를 프로덕션으로 바꾸면 됩니다. 개인이 만든 미검증 앱이어도 게시 자체는 막히지 않습니다. 대신 사용자 100명 한도와 "확인되지 않은 앱" 경고가 붙는데 혼자 쓰는 자동화라면 둘 다 문제가 되지 않습니다. 앱 이름은 자유롭게 바꿔도 되지만 로고를 올리는 순간 Google 검증 대상이 되니 올리지 않는 편이 낫습니다.

![Google Cloud 콘솔 대상 화면. 게시 상태가 프로덕션 단계로 표시되어 있고, OAuth 사용자 한도는 100명 중 1명이다](/images/gws-oauth-publish-status.png)

게시하고 나면 이 화면이 됩니다. 게시 상태가 "프로덕션 단계"로 바뀌고, 아래에 사용자 한도 100명 중 1명이 표시됩니다. 혼자 쓰는 자동화라 한도는 사실상 의미가 없습니다.

4. **게시만으로는 갖고 있던 토큰이 바뀌지 않습니다.** 버튼을 누르고 상태가 프로덕션으로 바뀐 걸 확인하고 끝냈다가 기존 토큰에 이미 7일 시한이 박혀 있다는 걸 뒤늦게 알았습니다. 테스트 시절에 발급된 것이라 그렇습니다. 게시한 다음 다시 인증해서 새 토큰을 받아야 비로소 만료가 사라집니다.

## 5. 인증을 고치자 그 아래 있던 고장이 드러났습니다

재인증에 성공하고 쓰는 서비스를 하나씩 불러봤습니다. Gmail과 Calendar는 정상이었는데 Tasks만 403을 냈습니다.

1. **401과 403은 다른 문입니다.** 401은 "당신이 누구인지 모르겠다", 403은 "누구인지는 알겠는데 그건 못 하게 되어 있다"입니다. 앞의 것은 인증, 뒤의 것은 권한 문제입니다. 두 달 동안 403이 안 보였던 이유가 여기 있습니다. 인증이 죽어 있는 동안 모든 요청이 첫 관문에서 막혔으니 두 번째 관문이 잠겨 있다는 사실을 알 방법이 없었습니다.

2. **스코프를 승인받는 것과 API를 켜는 것은 다른 일입니다.** 스코프는 앱이 요청하는 권한의 범위입니다. "Gmail 읽기", "캘린더 수정" 같은 항목이고 동의 화면에 목록으로 뜨는 게 바로 이것입니다. 사용자가 허용을 누르면 앱은 그 범위 안에서만 움직일 수 있습니다. 그런데 이건 사용자가 앱에게 주는 허락일 뿐입니다. 별도로 Google Cloud 프로젝트에서 해당 API를 사용 설정해 둬야 실제 호출이 나갑니다. 제 경우 Tasks 권한은 승인받았지만 프로젝트에서 Tasks API가 꺼져 있었습니다. 그래서 `accessNotConfigured`라는 403이 돌아왔습니다. 사용자 허락과 프로젝트 설정이 둘 다 있어야 호출이 성립합니다.

3. **스코프를 낮추려다 접었습니다.** 어차피 읽기만 하니 읽기 전용으로 내리면 덜 민감하겠다 싶었습니다. 확인하려고 코드에서 실제 호출부를 전부 뽑아봤더니 `gmail users drafts create`, `calendar events insert`, `events patch`, `events delete`가 이미 있었습니다. 읽기만 하는 게 아니었습니다. 낮췄으면 조용히 깨졌을 겁니다. 게다가 Gmail은 읽기 전용 스코프도 제한 스코프로 분류되어서 만료 정책과는 아무 상관이 없었습니다.

인증을 고쳤다고 끝이 아니었습니다. 서비스마다 한 번씩 실제로 불러봐야 그 아래 층의 고장이 보입니다. 스코프도 기억에 의존하지 말고 코드에서 확인해야 합니다.

## 6. 순서대로 붙이면 인증은 한 번입니다

돌아보면 방법이 아니라 순서가 문제였습니다. 인증부터 해놓고 나머지를 나중에 고치는 바람에 인증을 여러 번 했습니다. 아래 순서대로 하면 한 번이면 됩니다.

1. **동의 화면 게시를 가장 먼저 합니다.** 이걸 마지막에 하면 앞에서 받아둔 토큰이 전부 7일짜리라 재인증을 또 하게 됩니다. Google Cloud 콘솔의 대상(Audience) 화면에서 게시 상태를 확인하고 프로덕션으로 바꿉니다.

2. **필요한 API를 켜는 것도 인증보다 먼저입니다.** 안 켜두면 401 뒤에 403이 숨습니다. 쓸 서비스를 한 번에 켜두고 실제로 켜졌는지 확인합니다.

```bash
gcloud services enable gmail.googleapis.com calendar-json.googleapis.com \
  tasks.googleapis.com sheets.googleapis.com --project=<PROJECT_ID>

gcloud services list --enabled --project=<PROJECT_ID>
```

3. **스코프는 기억이 아니라 호출부에서 확정합니다.** 아래 명령은 코드 전체에서 gws 호출을 찾아 어떤 서비스에 어떤 동작을 시키고 있는지 목록으로 뽑습니다. `-r`은 하위 폴더까지, `-h`는 파일명 없이, `-o`는 매칭된 부분만 출력하라는 뜻이고 `sort -u`로 중복을 지웁니다. 결과에 `create`나 `insert` 같은 쓰기 동작이 하나라도 있으면 그 서비스는 읽기 전용으로 내릴 수 없습니다.

```bash
grep -rhoE "gws (gmail|calendar|tasks|sheets) [a-zA-Z]+ [a-zA-Z]+ ?[a-zA-Z]*" . | sort -u
```

4. **인증하고 나서 서비스별로 실제로 불러봅니다.** `token_valid: true`만 확인하고 끝내면 5번 섹션에서 겪은 403을 놓칩니다. 쓰는 서비스마다 한 번씩 호출해보고 자격증명 파일의 수정 시각이 갱신됐는지도 봅니다. 새 토큰을 실제로 받았다는 증거는 그 시각입니다.

5. **7일 뒤 확인은 사람이 기억하지 말고 자동화에 맡깁니다.** 게시가 실제로 먹혔는지는 7일을 넘겨봐야 압니다. 저는 매일 도는 스크립트의 인증 확인 부분에 토큰 나이를 함께 계산해 넣었습니다. 살아 있는데 8일이 넘었으면 7일 벽을 통과한 것이고 죽었을 때는 나이에 따라 원인이 갈립니다. 8일 안에 죽었으면 게시 상태를 의심하고, 그보다 오래됐으면 6개월 미사용이나 비밀번호 변경 같은 다른 조건을 봅니다.

```bash
AGE=$(( ( $(date +%s) - $(stat -f %m ~/.config/gws/credentials) ) / 86400 ))
```

무기한이라고 해서 영원한 건 아닙니다. 6개월 동안 안 쓰거나, Gmail 스코프를 물린 상태에서 계정 비밀번호를 바꾸거나, 권한을 철회하면 여전히 만료됩니다. 그래서 만료를 감지하는 장치는 그대로 뒀습니다.
