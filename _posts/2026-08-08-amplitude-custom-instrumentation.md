**TL;DR**

- autocapture가 못 잡는 것은 이벤트가 아니라 맥락입니다. 커스텀 이벤트 0개를 추가하고 프로퍼티 주입만으로 기존 이벤트 전부가 글 단위로 분석 가능해졌습니다.
- 완독을 스크롤 90%로만 판정하면 끝까지 튕겨 내려간 것과 구분되지 않습니다. 활성 체류시간을 AND로 걸었습니다.
- Amplitude는 수신한 이벤트를 tracking plan에 자동으로 넣지 않습니다. 이벤트가 보이는데 설명을 못 붙이는 상태에서 시간을 제일 많이 썼습니다.

autocapture를 다 켜두면 분석 준비가 끝난 걸까요? 이 블로그에 Amplitude를 붙일 때 저는 그렇게 생각했습니다. 클릭, 폼, 페이지뷰, 에러까지 전부 잡히니까요. 그런데 첫 질문에서 바로 막혔습니다. "어느 글이 제일 읽히나?"에 답할 수가 없었습니다. [지난번 SEO·GEO 설정 글](/posts/2026/07/github-pages-seo-geo-setup/)에서는 Amplitude를 설치했다는 것까지만 적고 넘어갔는데, 설치 다음에 무엇을 해야 분석이 시작되는지는 그때 쓰지 못했습니다. 그 다음 이야기를 이어 씁니다.

---

## 1. 이벤트를 늘리기 전에 프로퍼티부터 넣었습니다

분석이 안 되니 이벤트가 부족한 줄 알았습니다. 실제로 빠져 있던 것은 그 이벤트가 어디서 일어났는지였습니다.

1. **결핍은 이벤트 수가 아니라 컨텍스트였습니다.** `[Amplitude] Page Viewed`는 있지만 그 페이지가 어떤 글이고 어떤 카테고리이고 예상 읽기시간이 몇 분짜리인지는 이벤트에 없습니다. 그래서 새 이벤트를 만드는 대신 모든 이벤트에 프로퍼티를 주입하는 enrichment plugin 하나를 먼저 넣었습니다. 페이지가 자기 메타데이터를 전역 변수에 깔아두면, 플러그인이 모든 이벤트에 그것을 얹는 구조입니다. 한 가지 순서 함정이 있는데, 이 `add()`는 `amplitude.init()` 앞에 있어야 합니다. autocapture의 첫 pageView는 init 시점에 곧바로 발사되므로 플러그인을 나중에 등록하면 가장 중요한 첫 이벤트에 컨텍스트가 빠집니다. 이것을 넣는 순간 기존 autocapture 이벤트 전부가 글 단위로 분석 가능해졌고 그때까지 추가한 커스텀 이벤트는 0개였습니다.

```js
window.amplitude.add({
  name: 'blog-context-enrichment', type: 'enrichment',
  setup: function () { return Promise.resolve(undefined); },
  execute: function (event) {
    event.event_properties = Object.assign({}, window.__blogMeta || {}, event.event_properties || {});
    return Promise.resolve(event);   /* meta를 먼저 깔아 이벤트 고유 프로퍼티가 이기게 한다 */
  }
});
```

2. **커스텀 이벤트는 두 경우로만 만들었습니다.** 그다음에야 커스텀 이벤트를 추가했는데 기준을 두 개로 좁혔습니다. 첫째는 autocapture가 원리적으로 못 잡는 것으로, 스크롤 뎁스와 활성 체류시간, 검색 결과 수가 여기 해당합니다. 둘째는 잡히기는 하지만 이름이 무의미해서 차트를 못 만드는 것입니다. `Element Clicked`에 DOM 셀렉터만 붙어 있으면 사실상 조회가 불가능합니다. 이 두 경우가 아니면 프로퍼티로 해결하는 쪽이 항상 나았습니다. 이벤트가 늘수록 tracking plan 관리 비용도 같이 늘기 때문입니다.

순서를 뒤집었을 뿐인데 해결된 것이 많았습니다. 이벤트를 늘리는 일보다 이미 있는 이벤트에 의미를 붙이는 일이 먼저였습니다.

## 2. 완독은 스크롤만으로 판정하지 않습니다

블로그에서 제일 갖고 싶던 지표는 완독률이었습니다. 완독을 무엇으로 판정할지 정하는 데서 먼저 막혔습니다.

1. **스크롤 90%와 활성 체류시간을 AND로 걸었습니다.** 처음에는 스크롤 90%로 판정하려 했습니다. 그런데 스크롤 90%는 글을 다 읽은 것과 끝까지 튕겨 내려간 것을 구분하지 못합니다. 그래서 조건을 두 개로 걸었습니다. 스크롤이 90%에 닿는 동시에 활성 체류시간이 예상 읽기시간의 50% 이상일 때만 완독으로 봤습니다. 체류시간은 `visibilitychange`로 탭이 실제로 보일 때만 누적했습니다. 백그라운드에 열어둔 탭이 완독으로 잡히는 것을 막기 위해서입니다.

2. **델타로 보낸 체류시간은 SUM으로만 집계됩니다.** 체류시간은 탭 전환마다 직전 전송 이후의 델타로 보냈습니다. 이러면 페이지당 이벤트가 여러 번 발생합니다. 총 체류시간을 보려면 집계가 반드시 SUM이어야 하고 AVG는 무의미한 값이 됩니다. 이런 주의사항은 문서에 적어두는 것보다 Amplitude 이벤트 description에 박아두는 편이 낫습니다. 나중에 차트를 만들 때 UI에서 바로 보이기 때문입니다.

완독이라는 말 하나를 이벤트로 내리는 데 조건 두 개와 집계 방식 하나가 필요했습니다.

## 3. 보낸 이벤트가 tracking plan에 자동으로 들어가지 않습니다

여기서 시간을 제일 많이 썼습니다. 이벤트가 화면에 보이는데 설명을 붙일 수 없는 상태가 한동안 이해되지 않았습니다.

1. **이벤트는 세 단계를 거칩니다.** Amplitude는 수신한 이벤트를 tracking plan에 자동으로 편입하지 않습니다. 첫 단계는 존재하지 않음입니다. 코드에 있어도 한 번도 발생하지 않았으면 Amplitude에는 없는 이벤트입니다. 두 번째는 unexpected 상태로, 조회는 되지만 메타데이터를 붙일 수 없습니다. description을 수정하려 하면 "not in the tracking plan"이라며 거부됩니다. 세 번째가 plan 편입이고, 이것은 명시적으로 시켜야 합니다.

2. **편입 시점에는 description이 들어가지 않습니다.** 편입을 시키면 끝날 줄 알았는데 그렇지 않았습니다. 편입 호출 자체에는 description을 실을 수 없어서 편입한 다음 한 번 더 수정 호출을 해야 설명이 붙습니다. 즉 이벤트 하나에 메타데이터를 완비하려면 발생, 편입, 수정 세 번을 거칩니다. 문서에는 이 순서가 한 흐름으로 적혀 있지 않아서 직접 부딪히며 알아냈습니다.

계측은 코드를 배포한 시점이 아니라 이벤트가 plan에 자리를 잡은 시점에 끝납니다.

## 4. 환경이 계측 설계의 상한을 정합니다

계측 설계를 정한 것은 이론이 아니라 이 블로그가 놓인 조건이었습니다. 쓰고 싶어도 못 쓰는 도구가 있었고 쓰기 전에 한 번 더 생각하게 만드는 제약도 있었습니다.

1. **Ampli CLI는 CDN script loader 환경에서 쓸 수 없습니다.** 타입 안전 계측을 위해 Ampli CLI를 검토했습니다. 그런데 생성된 래퍼 코드를 `import`할 모듈 시스템과 npm SDK가 전제였습니다. 이 블로그는 Jekyll 정적 사이트라 CDN script loader로 SDK를 불러옵니다. 번들러가 없으니 생성된 코드를 넣을 자리 자체가 없었습니다. 이벤트가 10개 안쪽이면 마크다운 정의서로 충분하다고 결론 내렸습니다.

2. **소스가 공개 레포라 수집 항목이 코드로 드러납니다.** 검색 이벤트에는 검색어 원문을 보내지 않고 `query_length`만 보냈습니다. 그리고 이 블로그는 소스가 공개 레포라 계측 코드 자체가 누구에게나 보입니다. 무엇을 수집하는지가 코드로 공개된다는 것은 제약이면서 동시에 수집 항목을 보수적으로 유지하게 만드는 장치이기도 했습니다. 어차피 보인다고 생각하면 굳이 안 보내도 되는 값을 넣지 않게 됩니다.

둘 다 제가 고른 설계가 아닙니다. 환경이 먼저 선택지를 좁혔습니다.

---

## 내 생각

autocapture는 계측의 끝이 아니라 시작 상태입니다. 설치를 마쳤을 때 저는 분석을 시작할 수 있다고 생각했는데, 실제로 시작된 것은 수집뿐이었습니다. 이 간격이 생각보다 컸습니다.

돌아보면 이번에 한 일 중 효과가 가장 컸던 것은 코드량이 가장 적은 쪽이었습니다. enrichment plugin 하나로 이미 쌓이고 있던 이벤트 전부가 쓸모를 얻었습니다. 반대로 시간을 제일 많이 쓴 것은 tracking plan 편입처럼 기능과 무관한 절차였습니다. 계측 작업의 시간 배분은 대체로 이런 식으로 어긋납니다.

아직 데이터가 충분히 쌓이지 않아서 완독률 판정 기준이 맞는지는 확인하지 못했습니다. 스크롤 90%와 체류시간 50%라는 숫자도 근거를 따져서 정하지 않았습니다. 일단 잡아둔 값입니다. 실측이 쌓이면 이 기준부터 다시 볼 생각입니다.
